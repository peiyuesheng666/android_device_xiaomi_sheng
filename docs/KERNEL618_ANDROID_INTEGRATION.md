# Android 内核与模块分区集成

Android 的内核、设备树和可加载模块必须来自匹配的构建输入。内核迁移到 Linux 6.18 时，重新生成启动和 DLKM 分区的模块集合，不能沿用 Linux 5.15 的模块二进制或直接复制其加载清单。

| 分区 | 内容 |
| --- | --- |
| boot | 内核 Image 与内建驱动。 |
| vendor_boot | 第一阶段 init 所需模块的依赖闭包，以及单独确定的 Recovery 模块。 |
| vendor_dlkm | 其余设备、SoC 和厂商模块。 |
| system_dlkm | 与内核构建匹配的通用模块。 |

输入至少包含未嵌入模块归档的 Image、内核配置、Module.symvers、modules.dep、modules.builtin 和全部模块。根据设备树绑定、ELF 符号依赖、内建驱动及实际用户空间接口生成清单；名称不同本身不能作为移除模块的依据。

检查模块 ABI、符号校验、签名、加载顺序、固件路径和 SELinux 标签。不得修改 vermagic 或符号 CRC 来掩盖不兼容。

Qualcomm 电源与性能服务还依赖内核节点、拓扑、性能提示、状态事件和挂起唤醒接口。迁移时需配套审查 qcom-lpm、perfconfigs 和相关权限；模块加载成功不能替代接口适配。

设备树通过 BoardConfig、启动加载配置和模块准备工具消费这些输入。切换内核时应生成完整匹配的 boot、vendor_boot、vendor_dlkm、system_dlkm 与 Recovery 组合，并保留可恢复的原启动链。公共源码按 ROM 清单固定，设备适配和打包逻辑放在本设备树。

Android 变体的固定源码与工具链入口记录在 `interfaces/kernel/6.18/android-source.json`。
它独立于历史 HyperOS 原始 Image 计划。Android 使用内核阶段输出的 `kernel-Image`，
不运行参考项目的 `embed.sh` 或 `mkbootimage.sh`，不安装其 `k618_load.ko` 批量加载器。
真实硬件模块继续由原有 Android init 与 DLKM 加载流程管理。

`tools/plan_sheng_kernel_modules.py` 从同一次构建的 `modules.dep`、`modules.builtin`
和 `modules.softdep` 计算安装范围及加载顺序。要求文件使用 JSON，`roots` 必须明确列出
`first_stage`、`recovery`、`system_dlkm`、`vendor_dlkm` 四组根模块；`exclusions`
按模块名记录不纳入产品的理由。缺失依赖、名称冲突、循环或被排除的必要模块都会拒绝生成。
未解析的 softdep 也需要先核对对应配置和用途，不能直接删掉元数据使检查通过。
若驱动无条件声明了属于已禁用配置的可选 softdep，可在要求文件的
`optional_softdeps` 中逐项记录 `owner`、`dependency`、`config` 和 `reason`，
并传入实际构建的 `--kernel-config`。工具仅接受该配置明确为未启用、依赖确实不存在、
且规则精确匹配该依赖边的情况；真实硬依赖和显式要求的根模块仍不能缺失。
配置内容的哈希与每项可选依赖依据保留在计划中，不修改原始模块元数据。

第一阶段和 Recovery 的依赖闭包合并到 vendor_boot。所有保留的模块也必须在正常系统
的 DLKM 中有同一二进制的副本，与 ROM 原有源码内核的打包方式一致。切换根目录后
不能依靠 vendor ramdisk 文件参与正常系统的 depmod；已加载到内核也不代表依赖文件
可以缺失。仅 Recovery 加载的模块更不能被误认为正常 Android 已加载。
工具输出仅证明依赖规划结果；ABI、BTF、签名、硬件覆盖和实机启动仍须分别验证。
该计划不会自动切换 BoardConfig 或修改当前运行系统。

参考项目的 `profiles/module-sources.json` 仅描述其独立导出集合；Android 还要检查
同次构建的核心 `modules.order`，纳入 Recovery 日志、USB 外设等所需通用模块。
不能因模块不在参考导出清单中就认定它未配置或无需安装。核心与 SoC 的重复提供者
必须按 ABI 和具体实现明确选择，保留选择依据，不得混装两套同名或重复导出模块。

Android 配置差异记录在 `interfaces/kernel/6.18/android.config`。当前增加原厂 sheng
实际选择的 configfs RNDIS 功能；原厂共享 vendor.prop 的 `gsi` 会被设备专用 init
规则覆盖，不能把共用默认值当成本平板最终配置。应用片段后需重建 Image 和全部
配套模块，并重新校验 BTF 与符号。不能沿用片段应用前的验证结果。

Android 专用源码补丁按 `android-source.json` 的顺序应用到独立生成的内核输入，
不修改公共 ROM 源码或固定参考仓库。当前补丁处理以下真实依赖：

- GSI 与 configfs RNDIS 共享同一协议实现，避免重复导出符号。
- DWC3 使用本机 SNPS eUSB2 PHY；IPA 和视频保留 MDT 加载及 SCM 固件认证。
- GPU 的 TZ／带宽 governor 已链接到 KGSL 内部，GMU 频率查询 governor 仍须单独编译。
- PS5169 必须在其 `redriver` 符号提供者之后、DWC3 之前加载。
- 本机 `qcom,logbuf-vendor-hooks` 节点对应的原日志 minidump 模块必须保留。
- 两个 OEM 电源键 bark 中断分别保存实际 MTD／pmsg 日志和输出任务状态；保留正常按键事件及内核原生 panic/oops 回调，兼容已有日志头。
- 恢复真实的 MHI DTR／IP_CTRL 驱动及配置，上层 UCI 请求不再落到恒定返回 `-EIO` 的未启用分支。

电源键日志通知链以现用 5.15 模块二进制为准：PMIC 驱动提供原子的
`pwrkey_irq_notifier_list`，MTD 模块订阅长按事件。涉及睡眠的块设备写入转到高优先级
工作队列，卸载时注销通知并等待工作结束，设备移除与普通日志写入互斥。
普通电源键加载不应依赖日志存储初始化。该 OEM MTD 模块依赖 SoC 的真实通知接口，
因此由 SoC 阶段编译同一份核心 `mtdoops.c`；保留核心 MTD、原生 panic/oops 路径和
`CONFIG_MTD_OOPS`，不降低 modpost 检查级别。收集清单必须包含新位置的实际产物。

`module-migrations.json` 记录已核实的模块合并及源文件哈希。例如 `ns` 的实现和
初始化／退出已并入 `qrtr`；`rndisipam` 的真实网络与 IPA 数据通路已并入 `ipam`，
但其初始化仍由 `ipanetm` 执行，因此两者都需保留。其余旧模块继续逐项核查。

`module-collection.json` 的 `additional_modules` 明确列出参考导出清单遗漏、但本机
实际需要的模块。收集工具检查它们确实出现在同次构建的 `modules.order`，记录来源、
理由和哈希，然后与其他模块一起执行 ABI、BTF 和命名空间检查。不能仅复制同名文件。

OF compatible 对照只用于发现缺口。新版驱动可能改由真实的 platform 子设备注册，
例如 SCM 注册 `qcom-dload-mode`；应核对注册条件和驱动绑定。发现旧节点无匹配时，
不能只添加 compatible 字符串而不恢复对应行为。电源键 bark 诊断迁移已编译，pmsg
复制边界通过带 ASan／UBSan 的环形缓冲区测试，实际 IRQ／MTD 写入仍待验证。
当前检查不代表 Android 6.18 启动链、加密数据挂载或实机功能已经通过。

键盘的第 10 项补丁恢复现用原厂驱动 `Nanosic_PM_try_wakeup` 的 GPIO 握手：
写入前拉高物理 sleep 引脚，并等待真实 IRQ 引脚就绪，最多 100 次约 1ms。
超时或 GPIO 错误向调用方返回真实失败，不再每 12 秒发送强制电源指令。
认证和触控板功能状态仍由原厂 HAL 控制。恢复时保留首个真实输入包，
不再把首个 IRQ 当作无需处理的唤醒确认，也不因 25ms 未收到确认而重置 MCU。
系统唤醒 IRQ 按实际成功状态配对，卸载前解除唤醒引用，再释放 IRQ。
`tools/test_sheng_kernel_keyboard_wake.c` 测试同一生产 helper 的 GPIO 边界和
失败重试时的唤醒引用计数；实际系统休眠及输入效果仍需在新内核上回归。
